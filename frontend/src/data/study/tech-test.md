### DSA - Technical Question

#### Q. ArrayList/list/dynamic arrayとappend操作の時間計算量を説明してください

**回答:**

ほとんどの配列の実装では、アイテムを挿入するのに利用可能なスロットがない場合より大きなサイズ（通常は2倍）の新しい配列が作成されます[3]。アイテムは、古いArrayListから新しいArrayListにコピーされます[3]。配列は使用状況に応じて大きくなったり小さくなったりするため、動的であり、メモリ使用量も効率的です[3]。配列への挿入操作の時間的複雑さはO(1)です[3]。ただし、配列の容量が最大になり、拡張とコピーが必要になった場合は別です[3]。これはO(n)の処理です[3]。したがって、挿入操作の時間的複雑さを正しく表現するには、次のようになります。最大容量に達したときに：O(n), 各挿入操作のならし計算・償却（amortized）時間：O(1)[3]。

**参考リンク:** JAVA ARRAYLISTとLINKEDLIST

#### Q. ハッシュマップのルックアップの時間計算量を説明してください。また一般的なユースケースを説明してください。

**回答:**

ハッシュマップの検索にかかる平均時間はO(1)、最悪の場合はO(n)です[4]。ハッシュ関数によって、異なるキーが同じハッシュ値を持つ場合がありますが、この場合、ハッシュマップは、別のデータ構造（例えば、リスト）を使用して、キーの衝突を解決します[4]。平均的には、ハッシュ関数が均等に分布する場合、キーの衝突は少なくなり、ルックアップの時間計算量はO(1)になります[5]。ただし、ハッシュ関数が悪い場合、キーの衝突が多くなり、ルックアップの時間計算量はO(n)になる可能性があります[5]。一般的なユースケースとしては、データの高速な検索が挙げられます[5]。例えば、データベースのインデックスや、キャッシュの実装などがあります[5]。

**参考リンク:** Javaハッシュマップは本当にO（1）ですか？

#### Q. 二分探索木（Binary search tree）のルックアップの時間計算量を説明してください。また一般的なユースケースを説明してください。

**回答:**

二分探索木（Binary search tree）、ルックアップ操作にO(log n)を必要とし、大規模なデータセットを効率的に検索するのに有効であります[6]。ただし、二分探索木は、データの挿入や削除が頻繁になると平衡状態が保たれない実装を行うと偏った二分探索木になるため、最悪の場合検索が線形オーダーになります[6]。この場合、ルックアップの時間計算量がO(n)に近づく可能性があります[7]。効率を上げるためには、データの挿入や削除を行う際に、木の回転という操作を行い、常に平衡状態を保つAVL木や赤黒木を利用すると、検索・追加・削除が常にO(log n)となります[7]。

#### Q. キューとスタック、それぞれの使い分けについて説明してください

**回答:**

キューとスタックは、いずれも要素が順番に格納される線形データ構造である[8]。キューは先入れ先出し（FIFO）方式、スタックは後入れ先出し（LIFO）方式で運用されます[8, 9]。キューは、タスクの処理や、リクエストの処理など、順序が重要な場合に使用されます[8]。スタックは、関数の呼び出しや、履歴の管理など、最近の要素が重要な場合に使用されます[9]。

**参考リンク:** 【データ構造】キューとスタックの使い方を解説！【実用例たっぷり】

#### Q. データベースのインデックスはどのようなデータ構造を使用するのが最適なのか

**回答:**

データ構造の選択は使用ケースに依存します[10]。例えば、多くのユニークな値を持つ大きなテーブルのインデックスにはB-treeが最適かもしれませんが、少数の異なる値を持つ小さなテーブルのインデックスにはビットマップがより効率的かもしれません[10]。主なデータ構造として、B-tree、ハッシュテーブル、ビットマップ、トライ（Trie）が挙げられます[10-12]。B-treeは、検索、挿入、削除の操作を効率的に行うことができる自己平衡型の木構造データ構造で、特に大量のデータを保存するのに有効で、データが多数のディスクブロックに分散している場合でも高速アクセスが可能です[10, 11]。ハッシュテーブルは、キーが既知の場合、データへのアクセスがO(1)であります[10]。ビットマップは、少数の異なる値を持つカラムのインデックス付けに特に有効です[11, 12]。トライ（Trie）は、ツリー状のデータ構造で、特に文字列データの索引付けに有効です[11, 12]。

#### Q. グラフの探索アルゴリズム（BFS/DFS）について説明してください

**回答:**

グラフ探索には主にBFS（幅優先探索）とDFS（深さ優先探索）の2つのアルゴリズムがあります。BFSはキューを使用して、始点から近いノードから順に探索していきます。最短経路を求める問題に適しており、時間計算量はO(V+E)（V: 頂点数、E: 辺数）、空間計算量はO(V)です。DFSはスタック（または再帰）を使用して、できるだけ深くまで探索してからバックトラックします。トポロジカルソート、連結成分の検出、サイクル検出などに適しています。時間計算量はO(V+E)、空間計算量はO(V)です。

**参考リンク:** グラフの探索 - BFS/DFS

#### Q. ヒープ（優先度付きキュー）のデータ構造と時間計算量を説明してください

**回答:**

ヒープは完全二分木に基づくデータ構造で、最大値または最小値を効率的に取得できます。最小ヒープでは親ノードが子ノードより常に小さく、最大ヒープでは親ノードが子ノードより常に大きくなります。挿入と削除の時間計算量はO(log n)、最大/最小値の取得はO(1)です。ユースケースとしては、Top-K問題（大量データからK個の最大/最小値を効率的に取得）、ダイクストラ法による最短経路探索、タスクスケジューリング（優先度の高いタスクを先に処理）などが挙げられます。

**参考リンク:** ヒープとは？データ構造の基本を学ぼう

#### Q. 主要なソートアルゴリズムの時間計算量と使い分けを説明してください

**回答:**

主要なソートアルゴリズムの比較は以下の通りです。クイックソート：平均O(n log n)、最悪O(n²)。実用的に最も高速で、多くの標準ライブラリで採用されています。不安定ソートです。マージソート：常にO(n log n)。安定ソートで、外部ソート（メモリに収まらないデータ）にも適していますが、O(n)の追加メモリが必要です。ヒープソート：常にO(n log n)。追加メモリはO(1)ですが、キャッシュ効率が悪く実用的にはクイックソートより遅いことが多いです。バケットソート/基数ソート：O(n)で動作可能ですが、データの分布に依存し、適用範囲が限定されます。JavaScriptのArray.prototype.sort()はTimSort（マージソートと挿入ソートのハイブリッド）を使用しています。

**参考リンク:** ソートアルゴリズムまとめ

#### Q. Big-O記法（計算量の分析）について説明してください

**回答:**

Big-O記法は、アルゴリズムの効率を入力サイズnに対する計算量の上界として表現する方法です。定数倍や低次の項は無視し、最も支配的な項のみを表記します。主要な計算量クラスは以下の通りです。O(1)：定数時間（ハッシュマップのルックアップ）、O(log n)：対数時間（二分探索）、O(n)：線形時間（配列の全走査）、O(n log n)：線形対数時間（効率的なソート）、O(n²)：二次時間（二重ループ）、O(2^n)：指数時間（フィボナッチの再帰的計算）。面接では、自分が書いたコードの時間計算量と空間計算量の両方を説明できることが求められます。

**参考リンク:** 計算量オーダーの求め方を総整理

#### Q. 動的計画法（DP）とは何ですか？メモ化再帰との違いを説明してください

**回答:**

動的計画法は、問題を部分問題に分割し、各部分問題の結果を保存して再利用することで効率的に解を求める手法です。**最適部分構造**（最適解が部分問題の最適解から構成される）と**重複部分問題**（同じ部分問題が何度も出現する）の2つの性質を持つ問題に適用できます。

- **トップダウン（メモ化再帰）**: 再帰的に問題を解き、計算済みの結果をハッシュマップや配列にキャッシュする。直感的だが再帰のスタックオーバーフローに注意
- **ボトムアップ（テーブルDP）**: 小さな部分問題から順にテーブルを埋めていく。ループで実装するため再帰のオーバーヘッドがない

どちらも重複部分問題の再計算を避けることで、指数的な計算量を多項式時間に改善できます。代表的な問題: フィボナッチ数列、ナップサック問題、最長共通部分列（LCS）、コイン両替問題。

**参考リンク:** Dynamic Programming - GeeksforGeeks <https://www.geeksforgeeks.org/dynamic-programming/>

### Networking

#### Q. ブラウザでURLを開くと何が起こるのでしょうか？

**回答:**

DNSを通じて、クライアント（ブラウザ）はURLのホスト名を宛先サーバーのIPアドレスに解決します。そして、3ウェイハンドシェイクによりTCP接続を確立します。TCP接続の上に、TLSハンドシェイクによってTLS接続を確立し、暗号化されたデータのみがネットワーク上で送信されるようにします。クライアントはHTTPプロトコルを使用して、ヘッダーとリクエストペイロードを含むリクエストを送信先のサーバーに送信します。サーバーは、ステータスコード、ヘッダー、レスポンスペイロードで応答します。

**参考リンク:** GitHub - tetz-akaneya/what-happens-when-JA

#### Q. HTTP/2とHTTP/1.1の違いを教えてください

**回答:**

HTTP/2は複数のHTTPリクエストとレスポンスが1つのTCP接続上で同時に送受信できるようにします。HTTP/1.1 では、各リクエストと応答は1つのTCP接続で送受信されます。これにより、HTTP/2は帯域幅が限られているネットワークでは、パフォーマンスが大幅に向上する可能性があります。HTTP/2がバイナリフレーミングレイヤーを使用しているのに対し、HTTP/1.1はすべてのリクエストとレスポンスをプレーンテキスト形式で保持していることです。HTTP/2は、メッセージをバイナリ形式に変換してカプセル化することで、HTTPの効率を向上させています。HTTP/2は、サーバーがPUSHフレームを使用してクライアントにデータをプッシュすることができる点でも異なります

**参考リンク:** HTTP/2対HTTP/1.1：Webパフォーマンスにどのように影響するのか？, What is HTTP/2 and how is it different from HTTP/1?

#### Q. TCPとUDPの違いを説明してください。

**回答:**

TCPは、パケットの到着順序を正しくすること、パケットを失った場合の再送、IPパケットの重複処理など、UDPにはない信頼性の高い接続を確立しています。とはいえ、UDPはTCPよりも高速で効率的なプロトコルです。TCPはウェブサービスのような信頼性の高い接続を必要とするアプリケーションでよく使われ、UDPはマルチプレイヤーゲームや音声/ビデオ通話などパケットロスを許容できるアプリケーションでよく使われます。

**参考リンク:** TCP/IPとは？ | Cloudflare、UDPとは？ | Cloudflare

#### Q. TCPの3ウェイ・ハンドシェイクとは何ですか？

**回答:**

接続確立時、クライアントは SYN ビットを立てたパケットをサーバーに送信してハンドシェイクの開始を示します。サーバーは SYN を受信し、送信されたパケットの確認を示す ACK を返します。クライアントはサーバーからの返信を確認し、両者はデータを転送するために TCP 接続を確立します。(ボーナス) 接続を閉じるために、送信側 (クライアント/サーバー) は FIN パケットを送信します。受信側は FIN を受信し、確認を示す ACK を返します。送信側はその後 ACK で確認します。

**参考リンク:** Three Way Handshake

#### Q. TLS証明書は何のために使われるのですか？

**回答:**

TLS証明書は、ブラウザ、Webサイト、Webサイトのサーバー間で送信されるデータを暗号化することによって、インターネット接続を保護するために使用されます。TLS証明書は、データが改ざん、紛失、盗難されないように保証し、データが非公開で送信されることを保証します。TLS証明書は、電子メールや電子データの暗号化による保護にも使用されます。TLS証明書は、自分自身の身元を証明するだけでなく、電子メールや電子データの捺印にも使用されます

**参考リンク:** What is TLS、SSL/TLSサーバー証明書の基礎知識

#### Q. DNS（名前解決）とは何ですか

**回答:**

DNSとは、Domain Name Systemの略で、ドメイン名をIPアドレスに変換するプロセスです。このプロセスにより、ユーザーはURLを通してウェブサイトにアクセスすることができます。DNS解決は、ドメインネームシステム（DNS）によって実行され、IPアドレスをパブリックまたはプライベートインターネットに接続されたホストにマッピングします。DNS解決では、検索を実行したいプログラムがDNSリゾルバにリクエストを送信し、DNSリゾルバはDNSサーバーに問い合わせて、ドメイン名に関連付けられたIPアドレスを取得します。

**参考リンク:** What is Domain Name Resolution?

#### Q. HTTP/3とQUICプロトコルについて説明してください

**回答:**

HTTP/3はHTTPの最新バージョンで、TCPの代わりにUDPベースのQUICプロトコルを使用します。HTTP/2ではTCP上での多重化により、1つのパケットロスが全ストリームをブロックする「Head-of-Line Blocking」問題がありました。QUICはUDP上で独立したストリームを実装するため、あるストリームのパケットロスが他のストリームに影響しません。また、QUICはTLSハンドシェイクをトランスポート層のハンドシェイクと統合しており、接続確立が高速（0-RTTも可能）です。さらに、コネクションマイグレーション機能により、ネットワークが切り替わっても接続を維持できます。

**参考リンク:** HTTP/3 とは？ | Cloudflare <https://www.cloudflare.com/ja-jp/learning/performance/what-is-http3/>

#### Q. RESTful APIの設計原則について説明してください

**回答:**

RESTful APIは、Representational State Transferの原則に基づいたAPI設計スタイルです。主要な原則として以下があります。ステートレス性：各リクエストは完全に独立しており、サーバーはクライアントの状態を保持しません。リソース指向：URLはリソース（名詞）を表し、HTTPメソッド（GET/POST/PUT/DELETE）で操作を表現します。統一インターフェース：一貫した方法でリソースにアクセスします。適切なHTTPステータスコード：200（成功）、201（作成）、400（不正リクエスト）、404（未検出）、500（サーバーエラー）等を返します。HATEOAS：レスポンスに関連リソースへのリンクを含めることで、APIの探索性を高めます。

**参考リンク:** RESTful API 設計のベストプラクティス

#### Q. WebSocketとSSE（Server-Sent Events）の違いを説明してください

**回答:**

WebSocketは、クライアントとサーバー間の双方向通信を可能にするプロトコルです。最初のHTTPハンドシェイク後にプロトコルがアップグレードされ、持続的な全二重通信が可能になります。チャットアプリケーションやリアルタイムゲームなど、双方向のデータ交換が必要な場面で使用されます。一方、SSE（Server-Sent Events）はサーバーからクライアントへの一方向のデータストリームを提供します。通常のHTTP接続上で動作し、自動再接続機能を備えています。ニュースフィード、株価更新、通知など、サーバーからの一方向のリアルタイム更新に適しています。SSEはWebSocketよりもシンプルで、既存のHTTPインフラとの互換性が高いのが利点です。

**参考リンク:** WebSocket - Web API | MDN <https://developer.mozilla.org/ja/docs/Web/API/WebSocket>, Server-Sent Events 使用 - Web API | MDN <https://developer.mozilla.org/ja/docs/Web/API/Server-sent_events/Using_server-sent_events>

### Operating Systems

#### Q. プロセスとスレッドの違いとは？

**回答:**

プロセスとは、プログラムを実行するための環境で、次で構成されています。レジスタ、メモリアドレス空間、ファイルディスクリプタ、スレッドスタック。プロセスは、1つのシステム上で同時に実行でき、それぞれのプロセスには一意の識別子（プロセスID（PID）と呼ぶ）が含まれています。スレッドは実行可能なコンテキストであり、プロセスには1つ以上のスレッドが含まれています。プロセス内の各スレッドは独自のスタックを持っていますが、ヒープは共有されています。

**参考リンク:** プロセスとスレッドの概要

**回答:**

プロセスIDが分かれば、killプログラムを使ってプロセスを終了させることができます。内部では、プロセスに対してSIGKILLまたはSIGTERMシグナルが送信されます。どちらもプロセスを終了させることができますが、データの喪失などのリスクを避けるために、綺麗にプロセスを終了させるSIGTERMが推奨されます。

#### Q. カーネルモードとユーザーモードの違いを説明してください。

カーネルモードでは、プログラムはデバイスへのフルアクセスや特権命令の実行が可能です。ユーザープログラムはユーザーモードで動作し、システムコールを介してカーネルに特権的な操作を要求することができます。カーネルモードは高速に動作しますが、バグがあるとオペレーティングシステムが停止する可能性があります

#### Q. OSの仮想メモリについて説明してください

**回答:**

仮想メモリとは、各プロセスに独立した仮想アドレス空間を提供する仕組みです。MMU（Memory Management Unit）がページテーブルを使って仮想アドレスを物理アドレスに変換します。これにより、プロセス間のメモリ保護が実現され、各プロセスは他のプロセスのメモリに直接アクセスできません。また、物理メモリが不足した場合にはスワップ（ページアウト）によりディスクストレージに一時退避させることで、実際のRAM容量以上のメモリをプログラムに提供できます。ただし、スワップは物理メモリよりもアクセス速度が遅いため、頼りすぎるとシステムのパフォーマンスが低下します。

#### Q. デッドロックとは何ですか？また、その回避方法を説明してください

**回答:**

デッドロックとは、2つ以上のプロセス（またはスレッド）が互いに相手が保持しているリソースの解放を待ち続け、どちらも先に進めなくなる状態です。デッドロックが発生するには以下の4つの条件が同時に成立する必要があります。相互排他：リソースは一度に1つのプロセスしか使用できない。保持と待機：リソースを保持したまま他のリソースの取得を待つ。非横取り：他のプロセスが保持するリソースを強制的に奪えない。循環待ち：プロセス間でリソースの待機が循環する。回避方法としては、リソースの取得順序を統一する（循環待ちの排除）、タイムアウトを設定する、ロックの粒度を小さくする、データベースではデッドロック検出機能を活用する、などがあります。

**参考リンク:** デッドロック | Wikipedia <https://ja.wikipedia.org/wiki/%E3%83%87%E3%83%83%E3%83%89%E3%83%AD%E3%83%83%E3%82%AF>

#### Q. コンテキストスイッチとは何ですか？

**回答:**

コンテキストスイッチとは、CPUが現在実行中のプロセス（またはスレッド）の状態を保存し、別のプロセスの状態を復元して実行を切り替える処理のことです。保存される状態にはプログラムカウンタ、レジスタの内容、メモリマッピング情報などが含まれます。コンテキストスイッチにはオーバーヘッドが伴い、特にプロセス間のスイッチはスレッド間よりもコストが高くなります。これは、プロセス間ではメモリ空間の切り替え（TLBフラッシュ等）が必要なためです。過度なコンテキストスイッチはシステムパフォーマンスを低下させるため、スレッドプールの適切なサイジングやI/O多重化による最小化が重要です。

**参考リンク:** コンテキストスイッチ | Wikipedia <https://ja.wikipedia.org/wiki/%E3%82%B3%E3%83%B3%E3%83%86%E3%82%AD%E3%82%B9%E3%83%88%E3%82%B9%E3%82%A4%E3%83%83%E3%83%81>

#### Q. ACIDについて教えてください

**回答:**

ACIDについて説明すると、ACIDは原子性（Atomicity）、一貫性（Consistency）、分離性（Isolation）、耐久性（Durability）を表します。原子性は、トランザクションが失敗した場合には、データベース内のすべての更新が取り消され、再試行が安全であることを保証します。一貫性は、すべてのデータが定義されたルールに従って有効であることを保証します。分離性は、すべてのトランザクションが互いに分離され、同じデータに同時にアクセスすることがないようにします。耐久性は、データベースがクラッシュまたは再起動した場合でも、書き込まれたデータが失われないことを保証します。

#### Q. データベーストランザクションの分離レベルについて説明してください。

**回答:**

分離レベルは、複数のトランザクションが同じデータに同時アクセスする際のデータ競合を制御するために使用されます。4つの分離レベルがあり、上位ほど安全だがパフォーマンスコストが高くなります。

| 分離レベル | ダーティリード | ファジーリード | ファントムリード | 説明 |
|---|---|---|---|---|
| Read Uncommitted | 発生する | 発生する | 発生する | 他トランザクションのコミット前の変更も読み取れる。実務ではほぼ使わない |
| Read Committed | 防止 | 発生する | 発生する | コミット済みのデータのみ読み取れる。PostgreSQLのデフォルト |
| Repeatable Read | 防止 | 防止 | 発生する | 同一トランザクション内で同じクエリは同じ結果を返す。MySQL InnoDBのデフォルト。MVCC（マルチバージョン並行制御）で実装 |
| Serializable | 防止 | 防止 | 防止 | 完全な直列化。2段階ロック（MySQL InnoDB、SQL Server）、実際のシリアル実行（Redis）、SSI（PostgreSQL）で実装 |

#### Q. データベースインデックスとは何ですか？

**回答:**

インデックスは、データベースがデータを効率的に取得するのを助けるデータ構造です。主なインデックスの種類として、B-Tree（PostgreSQL、MySQL、範囲検索に強い）、ハッシュインデックス（等値検索に特化）、ログ構造マージツリー（SQLite、HBase、書き込みが多い場合に有利）があります。

- **複合インデックス**: 複数カラムにまたがるインデックス。**左端プレフィックスの原則**により、`(A, B, C)` の複合インデックスは `WHERE A =` や `WHERE A = AND B =` には使えるが、`WHERE B =` だけでは使えない
- **カバリングインデックス**: クエリに必要な全カラムがインデックスに含まれている場合、テーブル本体にアクセスせずインデックスだけでクエリを完結できる（Index Only Scan）
- **インデックスが効かないケース**: `LIKE '%文字列'`（前方一致でない）、カラムに関数を適用（`WHERE YEAR(created_at) = 2024`）、暗黙の型変換が発生する場合

**参考リンク:** DBのインデックスとは

#### Q. データベースインデックスによって書き込み性能が低下するのは何故ですか？

**回答:**

テーブルに新しいデータが追加されたり更新されたりすると、データベースはデータそのものと、関連するインデックスを更新しなければなりません。この操作自体が複数回の書き込みであるだけでなく、データベースはデータとインデックスが不可分操作（atomic operation）されることを保証する必要があります。不可分操作が実行されると、データベースは影響を受けるデータやインデックスに対してロックを取得し、トランザクションがコミットまたはロールバックされるまで、他のトランザクションがそれらにアクセスしたり変更したりできないようにすることがあります。データベースのロックは、以下を引き起こす可能性があります。同じロックがかかっているときに、他のトランザクションの待ち時間が発生して遅くなる, ロックの取得と解放のためのCPUとI/Oリソースの増加

#### Q. データベースレプリケーションを説明してください。

**回答:**

データを複製（レプリケーション）する理由はいくつかあります。より多くの読み取りクエリを処理するため、ユーザーに近いデータのコピーを持つため、バックアップ。書き込み先ログWALを使用してレプリカを構築できます（MySQLではbinary logを使う）。リーダーデータベースで書き込み操作が発生すると、ログをディスクに書き込み、ネットワークを介してフォロワーデータベースにログを送信します。ログがネットワークを介して送信されるため、遅延が発生する場合があり、これをレプリケーション遅延と呼びます。また、レプリケーションには同期レプリケーションと非同期レプリケーションがあります。同期レプリケーションは複製先からの応答を待ってから、複製元の処理を完了するレプリケーションです。複製先と複製元のデータが常に同期しているためデータ整合性が高く、データ損失が少ない。しかし、複製先からの応答を待つため、処理速度が遅くなるというデメリットがあります。一方で、非同期レプリケーションは複製先からの応答を待たずに、複製元の処理を完了するレプリケーションです。複製先と複製元のデータが同期していないため、データ整合性に問題が生じることがあるが処理速度が速くなるというのがメリットです。

**参考リンク:** データベースのレプリケーション

#### Q. RDBMSの障害復旧においてできることは何ですか？

**回答:**

一般的に、バックアップとリカバリーを使用することです。これは、定期的なバックアップ、オフサイトストレージ、復旧手順のテストが必要になります。データベースのバックアップは重いので頻繁に行われているわけでもなく復旧時にバックアップとともにログファイル（REDOログ、トランサクションログなど）でロールフォワードを使ったりします。しかし、この戦略では、回復ポイント目標（RPO）と回復時間目標（RTO）を0で達成することはできません。より良いRPOとRTOを達成するために、レプリケーションで別のノードを異なるアベイラビリティゾーンにデプロイすると達成できます。

#### Q. 共有ロックと排他ロックの違いについて説明して下さい

**回答:**

排他ロック（書き込みロックともいう）は、データベースの書き込みトランザクション内で使用され、他のトランザクションがデータから読み取ったり、データに書き込んだりするのを防止する。共有ロック（読み取りロックとも呼ばれる）は、他のプロセスがデータの指定された部分に対して書き込みロックを要求することを禁止します。ただし、他のプロセスは読み取りロックを要求することができます。この2種類のロックは、直列化可能性を保証するために2相ロック（2PL）を使用します。

#### Q. 楽観ロックと悲観ロックの違いについて説明してください

**回答:**

楽観ロックとは、他のトランザクションとの競合が起こりにくいという前提のもとで、データを更新する前にデータが取得した時と同じ状態であるかを確認し、更新することでデータの整合性を保証する方式です。楽観ロックでは、データ自体にはロックを掛けず、更新対象のデータがデータ取得時と同じ状態であることを判断するために、Version番号やタイムスタンプ等を使用することが一般的です。一方、悲観ロックは、他のトランザクションとの競合が起こりやすいという前提のもとで、データを更新する前に明示的にロックを掛けることで他のトランザクションからアクセスできないようにします。悲観ロックでは、データ更新後はロックの解放を必ず行う必要があります。楽観ロックは競合が少ない場合に有効であり、悲観ロックは競合が多い場合に有効です。また、楽観ロックはデータ自体にはロックを掛けず、悲観ロックは明示的にロックを掛けるため、楽観ロックの方がオーバーヘッドが少なくなります。

**参考リンク:** Optimistic vs. Pessimistic locking

#### Q. マテリアライズド・ビューとは

マテリアライズド・ビューは、クエリ仕様（ビュー定義のSELECT）から派生した事前計算されたデータセットで、後で使用するために保存されます。データは事前に計算されているため、マテリアライズド・ビューのクエリは、ビューのベース・テーブルに対するクエリを実行するよりも高速になります。しかし、中間結果を実体化することで、ストレージや計算リソースなどの追加リソースが発生するのがデメリットです。

#### Q. SQLインジェクションとは？また、それを対策する方法を教えてください。

**回答:**

SQLインジェクションとは、Webアプリケーションが使用するデータベースに不正なSQL文を送信（注入）する攻撃手法です。攻撃が成功すると、任意なSQL文が実行される可能性発生します。SQLインジェクションを防ぐためにはプリペアドステートメント（パラメタライズドクエリ付き）を使うこと、入力値を制限させる：入力値をそのままSQL文に埋め込むではなくそれを特定な値に変換する。例えばソートの構文を order by count {$USER_INPUT} ではなくorder by count {$USER_INPUT ? “ASC”: “DESC”} のように変換しておく、入力データに含まれる特殊文字（', ", \\など）をエスケープすることなどが挙げられます

#### Q. 正規化について教えてください

**回答:**

正規化とは、データベース設計の工程において同一テーブル内のデータの重複をなくすために、適宜データを分割・整理することです。正規化のメリットはデータの信頼性が高まる、データの更新が効率化される、データの冗長性が減り、データベースの容量が節約される、です。正規化には第一正規形、第二正規形、第三正規形などがあります。以下にそれぞれの定義を簡単に説明します：第一正規形: 同じ種類のデータが1つのカラムに格納されている表を分割し、各カラムには単一の値しか格納しないようにする。(リレーショナルデータベースでは既に第1正規形を満たす形式になっています)第二正規形: 第一正規形を満たし、かつ主キー（Primary Key）以外のカラムが主キーに完全に依存していない表を分割し、関連するカラムをグループ化する。第三正規形: 第二正規形を満たし、かつ非主キーのカラム間で推移的関数従属が存在しないようにする。

#### Q. N+1問題とは何ですか？また、その解決方法を教えてください

**回答:**

N+1問題とは、ORMを使用してデータベースからデータを取得する際に発生するパフォーマンス上の問題です。例えば、ユーザー一覧を1回のクエリで取得し（1回）、各ユーザーの投稿を個別にクエリで取得する（N回）場合、合計N+1回のクエリが発行されます。データ量が増えると、クエリの回数が線形に増加し、レスポンスタイムが大幅に悪化します。解決方法としては、Eager Loading（JOIN句やIN句を使って関連データを事前に一括取得する）、バッチ処理（複数のIDをIN句でまとめて取得する）、DataLoader（GraphQLなどで使用されるバッチング・キャッシングパターン）などがあります。

**参考リンク:** N+1問題とは？原因と解決方法

#### Q. データベースのシャーディングとパーティショニングの違いを説明してください

**回答:**

パーティショニングは、1つのデータベース内でテーブルを複数の部分に分割する手法です。水平パーティショニング（行の分割）と垂直パーティショニング（列の分割）があります。シャーディングは水平パーティショニングの一種で、データを複数の独立したデータベースサーバーに分散配置します。シャーディングの利点は、読み書きの負荷を複数サーバーに分散できること、データ量の上限を超えて拡張できることです。デメリットとしては、JOINが複雑になる、トランザクション管理が困難になる、シャードキーの選択が重要（ホットスポットの回避）、リシャーディングのコストが高い、などがあります。

**参考リンク:** データベースシャーディングとは | AWS <https://aws.amazon.com/jp/what-is/database-sharding/>

#### Q. スロークエリの分析方法を教えてください

**回答:**

スロークエリの分析には以下の手順を踏みます。まず、スロークエリログを有効にして、閾値を超えるクエリを特定します（MySQLではslow_query_log、PostgreSQLではlog_min_duration_statement）。次に、EXPLAIN（またはEXPLAIN ANALYZE）コマンドで実行計画を確認します。実行計画ではフルテーブルスキャン（Seq Scan）の有無、インデックスの使用状況、JOINの方法（Nested Loop/Hash Join/Merge Join）、推定行数と実際の行数の差異を確認します。改善策としては、適切なインデックスの追加、クエリの書き換え（サブクエリをJOINに変更等）、不要なカラムの取得を避ける（SELECT *の排除）、LIMIT/OFFSETの適切な使用などが挙げられます。

**参考リンク:** EXPLAIN の読み方 - PostgreSQL <https://www.postgresql.jp/document/current/html/using-explain.html>

### Distributed system

#### Q. コンシステントハッシュ法とは何ですか

**回答:**

コンシステントハッシュとは、ロードバランサー、KVデータベース（redis, Cassandra）のような複数のノードに負荷を均等に分散させるための方法である。負荷（例えばHTTPリクエスト）に基づいてハッシュを生成し、それを常にノードに割り当てています。新しいノードが追加されたり、ノードが削除されたりすると、システムはハッシュを再計算して、あるノードから別のノードに負荷を移動させる必要があり、これをリバランスと呼びます。複数のノードに負荷を均等に分散させるための方法ならmodulosハッシュもあるがリバランスのオーバーヘッドが大きいので（全てのノードのハッシュ値を再計算しないといけないから）コンシステントハッシュの方がスケールに優れています。

#### Q. 分散システムにおけるsplit brainについて教えてください。

**回答:**

分散システムにおいて、ネットワークパーティション（ノード間の通信断絶）が発生し、複数のノードが自分がリーダーだと思い込んでいる状態をスプリットブレインといいます。複数のリーダーが独立して書き込みを受け付けるため、データの不整合や破損が発生します。

**対策**:
- **クォーラム（Quorum）**: 過半数のノードの合意がなければリーダーとして認められない。ノード数2n+1に対してn+1の合意が必要。ZooKeeperやetcdがこの方式を採用
- **フェンシング（Fencing）**: 古いリーダーがリソースにアクセスできないよう強制排除する。フェンシングトークン（単調増加するID）を使い、古いトークンを持つリーダーの書き込みを拒否
- **リース（Lease）**: リーダーシップに有効期限を設定し、期限が切れたら再選出が必要。ネットワーク分断時に古いリーダーが自動的に失効する

#### Q. サーキットブレーカーパターンとは何ですか？

### Programming Language

#### Q. GCとは何ですか。また一番馴染みのあるプログラミングにおけるGCの仕組みを説明してください。

**回答:**

(JVM）JVM の GC は、世代別ガベージコレクションです。メモリ領域を「新世代領域（Young Generation）」と「旧世代領域（Old Generation）」に分けて管理します。新世代領域には新しく作成されたオブジェクトが配置され、旧世代領域には長期間生存したオブジェクトが配置されます。なお、JVM 8以降では「永続領域（PermGen）」は廃止され「メタスペース（Metaspace）」に置き換えられています。ガベージコレクタは、新世代領域を頻繁に掃除し、旧世代領域は定期的に掃除します。JVM の GC は、プログラマーの負担を軽減し、メモリリークを防ぐことができます。ただし、GC には、パフォーマンスの低下やガベージコレクションのタイミングによってはプログラムが停止するなどの問題もあります。JVM の GC には、いくつかの種類があります。最も一般的な GC は「マーク・コピー GC」です。マーク・コピー GC では、ガベージコレクタがまず使用されているオブジェクトをマークし、その後、マークされていないオブジェクトを解放します。(C++) C++ にはガベージ・コレクターがないためメモリ管理はプログラマによって手動で行う必要があります。メモリを管理する方法はいくつかありますが一般的な方法のひとつは、new と delete キーワードを使用することです。new キーワードはヒープ上にメモリーを割り当て、delete キーワードはメモリーを解放します。ガベージ・コレクターがないためオブジェクトが必要なくなったらメモリーを解放しないとメモリーリークが発生する可能性があります。また、動的確保したリソースを扱う場合、ポインタを扱う上での危険性（delete忘れたり、同じリソースを複数回deleteしたり）や負担を下げるために、 C++ ではスマートポインタという仕組みが存在します。

#### Q. 並行処理と並列処理の違いについて説明する。

**回答:**

並行処理（Concurrency）は「構造」であり、複数のタスクを論理的に同時に扱えるようにプログラムを構成すること。並列処理（Parallelism）は「実行モデル」であり、物理的に複数のタスクを同時に実行すること。

- **並行処理の例**: Goのgoroutine（シングルコアでも複数タスクを切り替えながら処理）、Node.jsのイベントループ（シングルスレッドでI/O待ちの間に別タスクを処理）
- **並列処理の例**: マルチスレッドでのCPUバウンド計算（JavaのparallelStream、PythonのmultiprocessingでCPUコアごとに別処理を同時実行）
- **関係**: 並行処理はシングルコアでも可能だが、並列処理にはマルチコアが必要。並行に構成されたプログラムをマルチコアで実行すると並列処理になる

Rob Pike: "Concurrency is about dealing with lots of things at once. Parallelism is about doing lots of things at once."

#### Q. SOLID原則について説明してください

**回答:**

SOLIDはオブジェクト指向設計の5つの基本原則です。単一責任の原則（SRP）：クラスは1つの理由でのみ変更されるべきです。開放閉鎖の原則（OCP）：拡張に対して開かれ、修正に対して閉じられているべきです。リスコフの置換原則（LSP）：サブクラスは親クラスの代わりに使用できるべきです。インターフェース分離の原則（ISP）：クライアントは自分が使わないインターフェースに依存すべきではありません。依存性逆転の原則（DIP）：高レベルモジュールは低レベルモジュールに依存すべきではなく、両者は抽象に依存すべきです。これらの原則を守ることで、保守性、テスト容易性、拡張性の高いコードを書くことができます。

### Scalability/Performance/Reliability

#### Q. 水平スケーリングと垂直スケーリングについて教えてください

**回答:**

水平スケーリングと垂直スケーリングの目的は、システムがより多くのトラフィック、負荷またはユーザーを処理できるようにすることである。両者の主な違いは、スケーリングする方向である：垂直スケーリングは、スケールアップとも呼ばれ、CPU、メモリ、ストレージ、ネットワーク帯域幅などのリソースを1台のマシンに追加して、より多くのリクエストを処理する能力を高めることです。しかし、より強力なマシンは常に高価であり、スケールアップできる上限があります。水平スケーリングは、スケールアウトとも呼ばれ、より多くのマシンやノードをシステムに追加して、増加するリクエストに対応します。この方法では、システムに追加された新しいマシンはそれぞれ他のマシンと並行して動作するように設計されており、ロードバランサーがトラフィックを均等に分散させるのが一般的です。バーティカル・スケーリングよりも拡張できる反面、ロードバランサーを追加することは、ネットワーク上のホップを増やすことを意味し、レスポンスの時間が余計にかかることになる。

#### Q. バックエンドシステムのパフォーマンスをどのように確保するのか？

**回答:**

バックエンドシステムの性能を確保するための一般的なアプローチをいくつか紹介します：可観測性： CPU使用率、メモリ使用率、ネットワーク遅延、データベースクエリなどのシステムメトリクスを観測可能なツールを使用して把握し、最適化が可能な箇所を特定する。負荷テスト： 本番環境でのトラフィックをシミュレートする負荷テストを実施し、高負荷時のシステム性能の問題を把握します。これにより、本番環境に導入する前にボトルネックを特定することができます。最適化を行う： システムのアーキテクチャ、コード、データベースクエリを最適化し、パフォーマンスを向上させる。これには、キャッシュ、ロードバランシング、コードプロファイリング、クエリの最適化などの技術が含まれます。スケーラビリティ（拡張性）： スケーラブルなアーキテクチャを実装することで、システムが負荷の増加に対応できるようにします。負荷が増加した場合に、システムがスケールアウト（水平方向）できるようにすることが方法の一つです。

#### Q. L4ロードバランサーとL7ロードバランサーの違いについて説明する。

**回答:**

L4のロードバランシングはトランスポートレイヤーで動作し、コンテンツを読み込むことなくネットワークパケットをただ転送します。L7のロードバランシングはアプリケーション層で動作し、メッセージの実際のコンテンツを読み込むことで、より多くの方法でネットワークトラフィックを転送することができます。L7ロードバランサーは、URLやクッキーなどのメッセージの内容に基づいて負荷分散を決定することができます。L7ロードバランサーは、ネットワークトラフィックを終了させ、メッセージを読み、選択されたアップストリームサーバーに新しいTCPコネクションを作成します。L4ロードバランサーは、ネットワークトラフィックに基づく単純なルーティングの決定を高速かつ効率的に行うことができ、L7ロードバランサーはより高度で、各メッセージの内容に基づく負荷分散の決定を行うことができますが、追加の処理が必要なため低速です。したがって、両者の選択は、アプリケーションの特定のニーズと、速度と機能の間のトレードオフに依存します。

#### Q. サービスレベル指標（SLI）、サービスレベル目標（SLO）、サービスレベル合意（SLA）とは何ですか？

#### Q. キャッシュ戦略について説明してください

**回答:**

キャッシュ戦略にはいくつかのパターンがあります。Cache-Aside（Lazy Loading）：アプリケーションがまずキャッシュを確認し、ミスの場合にDBから取得してキャッシュに格納します。最も一般的なパターンです。Write-Through：データの書き込み時にキャッシュとDBの両方に同時に書き込みます。データの一貫性は高いですが、書き込みレイテンシが増加します。Write-Behind（Write-Back）：データをまずキャッシュに書き込み、非同期でDBに反映します。書き込み性能は高いですが、キャッシュ障害時にデータ損失のリスクがあります。Read-Through：キャッシュ自身がDBからデータを取得する責務を持ちます。キャッシュの有効期限（TTL）の設定、キャッシュの無効化戦略（イベントベース、TTLベース）も重要な設計要素です。

**参考リンク:** キャッシュ戦略 | AWS <https://aws.amazon.com/jp/caching/best-practices/>

#### Q. レート制限（Rate Limiting）の実装方法を教えてください

**回答:**

レート制限は、特定の時間枠内でクライアントが送信できるリクエスト数を制御する仕組みです。主要なアルゴリズムとして以下があります。トークンバケット：一定の速度でトークンが補充され、リクエストごとにトークンを消費します。バーストトラフィックにも対応でき、最も広く使われています。リーキーバケット：リクエストをキューに入れ、一定のレートで処理します。出力が均一になる特徴があります。固定ウィンドウカウンター：固定の時間枠内でリクエスト数をカウントします。ウィンドウの境界でバーストが発生する問題があります。スライディングウィンドウ：固定ウィンドウの欠点を改善し、直近の時間枠で正確にカウントします。実装にはRedisなどのインメモリストアが使われ、APIゲートウェイ（Nginx、API Gateway）やアプリケーションミドルウェアで適用されます。

**参考リンク:** Rate Limiting パターン | Microsoft Learn <https://learn.microsoft.com/ja-jp/azure/architecture/patterns/rate-limiting-pattern>

### Authentication / Authorization

#### Q. OAuth 2.0の認可フローについて説明してください

**回答:**

OAuth 2.0は、サードパーティアプリケーションがユーザーの認証情報を直接扱わずにリソースへのアクセスを委任するための認可フレームワークです。主要なフローとして以下があります。

- **Authorization Code Flow**: Webアプリ向け。ユーザーが認可サーバーで認証→認可コード発行→サーバー側でコードをアクセストークンと交換。最もセキュアなフロー
- **Authorization Code Flow with PKCE**: SPAやモバイルアプリ向け。コードベリファイア（ランダム文字列）とコードチャレンジ（そのハッシュ）で認可コードを保護し、クライアントシークレットなしでも安全に実行
- **Client Credentials Flow**: サーバー間通信（M2M）向け。ユーザーの介在なしでクライアントIDとシークレットでトークンを取得
- **OpenID Connect（OIDC）**: OAuth 2.0の上に認証レイヤーを追加した規格。IDトークン（JWT）でユーザーの身元を確認

**参考リンク:** OAuth 2.0 — OAuth <https://oauth.net/2/>

#### Q. セッションベース認証とトークンベース認証の違いを説明してください

**回答:**

- **セッションベース認証**: サーバー側にセッション情報を保持し、CookieでセッションIDをやり取りする。ステートフル。サーバーのメモリやDBにセッションを保存するため、水平スケーリング時にはセッション共有（Redis等）が必要

### DevOps / CI/CD

#### Q. ブルーグリーンデプロイメントとカナリアリリースの違いを説明してください

**回答:**

- **ブルーグリーンデプロイメント**: 現行環境（Blue）と新環境（Green）を並行運用し、ロードバランサーの切り替えで一括移行する。ロールバックが容易（Blueに切り戻すだけ）だが、同時に2倍のリソースが必要

- **ローリングデプロイ**: インスタンスを順次更新していく。リソース効率は良いが、新旧バージョンが混在する期間が発生する

**参考リンク:** Deployment Strategies Defined - Harness <https://www.harness.io/blog/deployment-strategies>

### Observability

#### Q. オブザーバビリティの3本柱について説明してください

**回答:**

オブザーバビリティ（可観測性）とは、システムの外部出力からその内部状態を推測できる度合いのことです。3本柱で構成されます。

- **ログ（Logs）**: 離散的なイベントの記録。構造化ログ（JSON形式）が推奨され、検索・フィルタリングが容易になる。ELKスタック（Elasticsearch + Logstash + Kibana）やCloudWatch Logsなどで集約
- **メトリクス（Metrics）**: 数値データの時系列集計。CPU使用率、メモリ、レスポンスタイム、エラーレート等。Prometheus + Grafanaが代表的。RED（Rate, Errors, Duration）やUSE（Utilization, Saturation, Errors）メソッドで重要なメトリクスを体系化
- **トレース（Traces）**: リクエストがシステムを横断する際の処理経路を追跡する分散トレーシング。ボトルネックの特定やサービス間の依存関係の可視化に有効。OpenTelemetry、Jaeger、Zipkinが代表的なツール

### API Design

#### Q. APIにおける冪等性（Idempotency）とは何ですか？なぜ重要ですか？

**回答:**

冪等性とは、同じ操作を何度実行しても結果が変わらない性質のことです。HTTPメソッドでは、GET、PUT、DELETEは冪等であるべきだが、POSTは冪等ではありません。

冪等性が重要な理由は、ネットワーク障害やタイムアウト時にクライアントがリクエストをリトライしても安全であることを保証するためです。例えば、決済APIでタイムアウトが発生した場合、リトライで二重決済が発生しないようにする必要があります。

実装方法としては、**Idempotency Key**（リクエストに一意のキーを付与し、サーバー側で重複を検出する）が一般的です。Stripe APIがこの方式を採用しています。

**参考リンク:** Idempotency - MDN Web Docs Glossary <https://developer.mozilla.org/en-US/docs/Glossary/Idempotent>

#### Q. モノリスとマイクロサービスの使い分けの判断基準は？

**回答:**

- **モノリス**: 全機能が1つのデプロイ単位。プロジェクト初期や小規模チームではシンプルで開発・デバッグ・デプロイが容易。Martin Fowlerの「Monolith First」アプローチが推奨される
- **マイクロサービス**: 機能ごとに独立したサービスに分割。チーム規模が大きくなり、独立したデプロイ・スケーリング・技術選定が必要になった段階で検討する。ただし、サービス間通信、分散トランザクション、運用の複雑さというトレードオフがある

モノリスでドメイン境界が明確になってから段階的にサービスを分離するのが現実的です。最初からマイクロサービスで始めるのは、ドメイン知識が不足している段階ではサービス境界を誤るリスクが高いためアンチパターンとされています。

**参考リンク:** Monolith First - Martin Fowler <https://martinfowler.com/bliki/MonolithFirst.html>

#### Q. SQLデータベースとNoSQLデータベースの使い分けを説明してください

**回答:**

- **SQL（RDB）**: 構造化データ、複雑なクエリやJOIN、ACID準拠が必要な場合に適する。金融、EC等のトランザクション整合性が重要なシステム。PostgreSQL、MySQL
- **NoSQL**: スキーマの柔軟性、水平スケーリング、高スループットが求められる場合に適する
  - ドキュメント型（MongoDB）: スキーマレス、アプリケーションのオブジェクト構造と親和性が高い
  - KVS（Redis, DynamoDB）: シンプルなキーアクセス、キャッシュ、セッション管理
  - 列指向（Cassandra）: 大量の書き込み、時系列データ
  - グラフ（Neo4j）: 関係性のトラバーサルが主要なユースケース

選定基準: データモデルの複雑さ、スケール要件、一貫性要件、チームの習熟度。CAP定理のトレードオフも考慮する。

**参考リンク:** SQL vs NoSQL: 5 Critical Differences <https://www.integrate.io/blog/the-sql-vs-nosql-difference/>

#### Q. プリミティブ型とオブジェクト型の違いは何ですか？

**回答:**

プリミティブ型はイミュータブル（immutable）で値そのものを格納していますが、オブジェクト型はデフォルトではイミュータブルではなく、プロパティを後から変更できます。関数の引数に渡す際もプリミティブ型は値がコピーされて渡されますが、オブジェクトは参照の値が渡されます（call by sharing）。そのため関数内でプロパティを変更すると元のオブジェクトに反映されますが、引数自体に新しいオブジェクトを再代入しても元の変数には影響しません。また比較する際もプリミティブ型が同じ値（例: const color = ‘blue’）の場合は trueを返しますが、オブジェクトの場合は同じプロパティの値を持った2つのオブジェクト同士を比較しても、異なる参照をしているので falseを返します [20]。

**参考リンク:** 【JavaScript】プリミティブ型とオブジェクト型を理解したい - Qiita <https://qiita.com/ta1fukumoto/items/effaa42cd296a2648d41>, プリミティブ型 (primitive types) | TypeScript入門『サバイバルTypeScript』 (typescriptbook.jp) <https://typescriptbook.jp/reference/values-types-variables/primitive-types>

#### Q. イベントバブリングとは何ですか？

2. ターゲットフェーズ – イベントがターゲット要素に到達しました。

#### Q. JavaScriptのthisの挙動について説明してください（call/apply/bind、アロー関数を含む）

**回答:**

JavaScriptでは、thisキーワードはオブジェクトの事を指します。どのオブジェクトを指すかは、thisがどのように呼び出されるかに依存します。
- オブジェクトメソッド obj.method() では、オブジェクト obj を指します。
- グローバルコンテキストで呼ぶと、グローバルオブジェクトを指します。ブラウザ上では windowを指します。
- 関数コンテキストで呼ぶと、グローバルオブジェクトがデフォルトでバインディングされます。なお、Strictモードでは undefinedとなります。
- イベントハンドラの中では、イベントを受け取った HTML 要素（HTMLElement）を指します。
- apply, call, bind で関数（例えばfunc.call(obj)）を呼ぶと、引数として渡されるオブジェクト obj を指します。call()はカンマ区切りの引数、apply()は配列で引数を渡す違いがあります。
- アロー関数は独自のthisを持たず、定義時のレキシカルスコープのthisを参照します。そのため、コールバック関数でthisを保持したい場合に有用です。

#### Q. Cookie、sessionStorage、localStorageの違いについて説明して下さい

#### Q. JavaScriptエンジンのV8はどのように動作していますか？

**回答:**

V8は以下のステップで動作します。
1. *JavaScript source*: ソースコードがV8エンジンに提供される [52]。
2. *Parse it*: パーサーによりソースコードが解析されトークンに分解される [53]。
3. *AST (Abstract Syntax Tree)*: パーサーがトークンを組み合わせてASTを生成する [53]。
4. *Generate Bytecode*: インタープリターIgnitionがASTを低レベルのバイトコードに変換する [53]。
5. *Get feedback (Profiling)*: バイトコード実行中に実行情報（HotSpotなど）を収集する [53]。
6. *Optimize and Compile it*: JITコンパイラTurboFanがフィードバックを元にコードを最適化する（最適化の仮定が間違っていた場合はデオプティマイズも行う） [53]。

#### Q. React.memoとは何ですか？いつ使うべきですか？

**回答:**

React.memoは、コンポーネントをメモ化する高階コンポーネント（HOC）です。propsが変更されない限り、コンポーネントの再レンダリングをスキップします。React.memoはデフォルトでpropsの浅い比較（shallow comparison）を行いますが、第2引数にカスタム比較関数を渡すことも可能です。使うべき場面としては、レンダリングコストが高いコンポーネント、親コンポーネントが頻繁に再レンダリングされるが自身のpropsは変わらない場合、リストの各アイテムコンポーネントなどです。ただし、メモ化自体にもコストがかかるため、すべてのコンポーネントに適用すべきではなく、プロファイリングで実際にパフォーマンス問題が確認された箇所に使用すべきです。

#### Q. useReducerはいつ使うべきですか？useStateとの使い分けを教えてください

**回答:**

useReducerは、複雑な状態ロジックを管理するためのフック関数です。useStateとの使い分けの基準は以下の通りです。useReducerが適している場面：状態の更新ロジックが複雑な場合（複数のアクションタイプがある）、次の状態が前の状態に依存する場合、複数の関連する状態値をまとめて管理したい場合。useStateが適している場面：単純な値の管理（boolean、文字列、数値等）、独立した状態値の管理。useReducerはReduxと同様のパターン（dispatch + action + reducer）を使用するため、状態遷移が予測可能でテストしやすいという利点もあります。Contextと組み合わせることで、簡易的なグローバル状態管理として使用できます。

#### Q. Next.jsのSSR、SSG、ISRの違いを説明してください

**回答:**

Next.jsでは主に3つのレンダリング戦略があります。SSR（Server-Side Rendering）：リクエストのたびにサーバーでHTMLを生成します。常に最新のデータを表示できますが、リクエストごとにサーバー処理が必要でTTFB（Time to First Byte）が遅くなる可能性があります。SSG（Static Site Generation）：ビルド時にHTMLを生成します。CDNからの配信が可能で最も高速ですが、データの更新にはビルドの再実行が必要です。ISR（Incremental Static Regeneration）：SSGの拡張で、指定した時間間隔でバックグラウンドでページを再生成します。SSGの高速さとSSRのデータ鮮度を両立できます。Next.js 13以降のApp Routerでは、Server Componentsがデフォルトで、fetch関数のcacheオプションやrevalidateオプションでこれらの戦略を制御します。

**参考リンク:** Rendering | Next.js <https://nextjs.org/docs/app/building-your-application/rendering>

#### Q. ブラウザがHTMLをダウンロードを完了してから画面に描画されるまでのステップを説明してください

#### Q. クリティカルレンダリングパスとは何ですか？

**回答:**

#### Q. Resource Hintsとは何ですか？

#### Q. Webアプリケーションのページ表示速度や遅くUI操作も重いと言われました。あなたは何をして改善しますか？

**回答:**

Webアプリケーションのページ表示速度を向上させ、UI操作の重さを軽減するために、以下の手順を実行できます。
1. *パフォーマンスを分析する: *パフォーマンス分析ツール（Google Lighthouseなど）を使用して、ボトルネックを特定する [113, 114]。
2. *画像を最適化する: *画像を圧縮しWebPやAVIFのような適切な形式で提供する。画像を遅延ロードする [114]。
3. *アセットを最小化および圧縮する: *HTML、CSS、JavaScriptファイルの圧縮を行い [114]、サーバーでGZIPまたはBrotli圧縮を有効にする [115]。
4. *JavaScriptを最適化する: *使用されていないコードを削除（Tree shaking）、非クリティカルなJSを遅延、大きなファイルを分割する [115]。
5. *CSSを最適化する: *使用されていないCSSを削除し、初期レンダリングに必要なスタイルをインライン化する [115]。
6. *HTTP/2を使用する: *ストリームの多重化やHPACK圧縮アルゴリズムを活用する [115]。
7. *ブラウザーキャッシングを活用する: *適切なキャッシュヘッダーを設定し、必要ならService Workerを活用する [115]。
8. *Content Delivery Network（CDN）を使用する: *CDNを使用して、ユーザーに近いサーバーから静的アセットを提供する [115]。
9. *Resource Hintsおよび103 Early Hintsを使用する: *重要なリソースを事前に読み込みまたはフェッチし、コネクションを確立する [116]。
10. *UIを簡素化する: *UI要素、アニメーション、トランジションの数を減らし、レンダリングオーバーヘッドを最小限に抑える [116]。
11. *仮想化ページネーションされたリストを使用する: *大規模なリストを扱う場合、仮想化またはページネーションを実装する [116]。

#### Q. クロスサイトスクリプティング（XSS）とは？また、それを対策する方法を教えてください。

**回答:**

XSS攻撃を成功させるためには、攻撃者がHTMLに悪意のコードを挿入して実行する必要があります [121]。防ぐには、HTMLに出力される変数を処理する必要があります [121]。具体的には
- 出力エンコード：JavaScriptの場合は.textContentを使ってHTMLエンコードを行う [121]
- HTMLでのサニタイズ：変数から危険なHTMLを取り除き、安全なHTMLの文字列を返します。OWASPは、HTMLサニタイズにDOMPurify <https://github.com/cure53/DOMPurify>を推奨しています [121]。

**参考リンク:** Cross Site Scripting Prevention Cheat Sheet <https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html#html-sanitization>

#### Q. CORSとは何ですか？

**回答:**

CORSとは、オリジン間リソース共有 (Cross-Origin Resource Sharing) の略で、異なるオリジンからのアクセスを許可する仕組みです [123]。CORSがなければ、ブラウザーはセキュリティ上の理由でリクエストを拒否します [123]。CORSを有効にするには、サーバー側でアクセスを許可するオリジンやメソッドなどを指定するHTTPヘッダーを返す事が必要です [124]。

CORSにはSimple RequestとPreflight Requestの2種類がある:
- **Simple Request**: GET/HEAD/POST かつ Content-Type が `text/plain`, `multipart/form-data`, `application/x-www-form-urlencoded` のいずれかの場合、プリフライトなしで直接リクエストが送信される
- **Preflight Request**: 上記以外（PUT/DELETE、`application/json` のPOST、カスタムヘッダー付きなど）の場合、ブラウザが事前に OPTIONS メソッドでプリフライトリクエストを送信し、サーバーが `Access-Control-Allow-Methods` / `Access-Control-Allow-Headers` で許可を返した後に本リクエストが送信される

**参考リンク:** オリジン間リソース共有 (CORS) - HTTP | MDN (mozilla.org) <https://developer.mozilla.org/ja/docs/Web/HTTP/CORS>

#### Q. CSRF（クロスサイトリクエストフォージェリ）とは何ですか？また、その対策方法を教えてください

**回答:**

CSRFとは、攻撃者が被害者のブラウザを利用して、被害者が認証済みのWebサイトに対して意図しないリクエストを送信させる攻撃手法です。例えば、被害者がオンラインバンキングにログイン中に、攻撃者のサイトにアクセスすると、ブラウザが自動的にCookieを送信するため、不正な送金リクエストが実行される可能性があります。対策としては、CSRFトークン：サーバーがフォームに一意のトークンを埋め込み、リクエスト時に検証する。SameSite Cookie属性：CookieにSameSite=Strict またはSameSite=Laxを設定し、クロスサイトリクエストでのCookie送信を制限する。Originヘッダーの検証：リクエストのOriginヘッダーが期待するドメインと一致するか確認する、などがあります。

**参考リンク:** Cross-Site Request Forgery Prevention Cheat Sheet | OWASP <https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html>

#### Q. Same-Origin Policyとは何ですか？

**回答:**

Same-Origin Policy（同一オリジンポリシー）は、Webブラウザに実装されているセキュリティメカニズムで、あるオリジン（スキーム + ホスト + ポートの組み合わせ）から読み込まれたドキュメントやスクリプトが、異なるオリジンのリソースにアクセスすることを制限します。例えば、https://example.com から読み込まれたJavaScriptは、https://api.other.com のデータを直接取得できません。これにより、悪意あるサイトがユーザーの認証情報を利用して別サイトのデータを読み取ることを防ぎます。ただし、<img>、<script>、<link>タグによるリソースの読み込みは許可されています。異なるオリジンとの通信が必要な場合は、CORSを使用します。

**参考リンク:** 同一オリジンポリシー - Web セキュリティ | MDN <https://developer.mozilla.org/ja/docs/Web/Security/Same-origin_policy>

#### Q. CSP（Content Security Policy）とは何ですか？

**回答:**

CSP（Content Security Policy）は、XSSやデータインジェクション攻撃を軽減するためのセキュリティレイヤーです。HTTPレスポンスヘッダー（Content-Security-Policy）で定義し、ブラウザが実行・読み込みを許可するリソースのソースを制限します。例えば、`Content-Security-Policy: default-src 'self'; script-src 'self' https://trusted.cdn.com` と指定すると、自サイトと指定CDNからのスクリプトのみ実行を許可し、インラインスクリプトや他のドメインからのスクリプトはブロックされます。CSPの主要なディレクティブとして、default-src（デフォルトのソース）、script-src（スクリプトのソース）、style-src（スタイルのソース）、img-src（画像のソース）などがあります。

**参考リンク:** Content Security Policy (CSP) - HTTP | MDN <https://developer.mozilla.org/ja/docs/Web/HTTP/CSP>

#### Q. JWT（JSON Web Token）の仕組みと注意点を教えてください

**回答:**

JWTは、JSON形式で情報を安全に伝達するためのトークン規格です。Header（アルゴリズムとトークン種別）、Payload（クレーム/ユーザー情報）、Signature（署名）の3つのパートをBase64URLエンコードしてドット区切りで結合した文字列です。サーバーは秘密鍵で署名を検証することで、トークンが改ざんされていないことを確認できます。注意点として、Payloadは暗号化されていないためBase64デコードで内容を読める（機密情報を含めない）、トークンの失効管理が難しい（有効期限を短く設定し、リフレッシュトークンと組み合わせる）、localStorageに保存するとXSSリスクがある（HttpOnly Cookieでの管理が推奨される場合もある）、トークンサイズが大きくなりやすい、などが挙げられます。

**参考リンク:** JSON Web Token Introduction - jwt.io <https://jwt.io/introduction>

### Frontend Testing

#### Q. フロントエンドのテスト戦略について説明してください

**回答:**

テストピラミッド（またはテストトロフィー）に基づいて設計します。

- **ユニットテスト**: 個々の関数やカスタムフックの単体テスト。Jest、Vitest。実行速度が速くコストが低い
- **コンポーネントテスト**: UIコンポーネントの描画とユーザーインタラクション。React Testing Library。実装詳細ではなくユーザーの振る舞いをテストする
- **統合テスト**: 複数コンポーネントの結合テスト。Testing Library + MSW（Mock Service Worker）でAPI通信をモック。Kent C. Doddsのテストトロフィーでは、最もコストパフォーマンスが高いこの層に重点を置くことを推奨
- **E2Eテスト**: 実際のブラウザでユーザーシナリオを自動テスト。Playwright、Cypress。信頼性は最も高いが実行コストが高く遅い

**参考リンク:** Testing Trophy and Testing Classifications - Kent C. Dodds <https://kentcdodds.com/blog/the-testing-trophy-and-testing-classifications>

#### Q. 次の出力は何になりますか？

```javascript
console.log(0.1 + 0.2 == 0.3);
```

**回答:**

答え: false
JavaScriptで0.1 + 0.2 ≠ 0.3となるのは、JavaScriptが浮動小数点数を2進数で表現しているため、特定の10進数を表現できないからです [126, 127]。JavaScriptはIEEE 754の規格に従って、JavaScriptは浮動小数点数について約 17 桁の精度しか保持できません [127]。

#### Q. 次の出力は何になりますか？

```javascript
for (var i = 0; i < 3; i++) {
```

答え: 3, 3, 3

setTimeout()関数はイベントキューに追加され、ループを抜けた後で実行されます [128]。変数iはvarで宣言されているため、巻き上げ（*ホイスティング*）が起き、ループを抜けた後の値（3）が参照されます [128]。

#### Q. 次の出力は何になりますか？

```javascript
console.log('one');
```

**回答:**

#### Q. 次の出力は何になりますか？

```javascript
Promise.resolve(1)
.then(
(value) => console.log(value * 2),
)
.then(() => { throw new Error('Oh No!'); })
.catch((error) => 3)
.finally(() => console.log(4))
.then(console.log);
console.log(7);
```

**回答:**

答え: 7, 2, 4, 3

**解説（実行順序）:**

1. `console.log(7)` — 同期処理なので最初に実行される → **7** を出力
2. `Promise.resolve(1)` → resolved(1) がマイクロタスクキューに入る
3. `.then(value => console.log(value * 2))` → **2** を出力。明示的なreturnがないため resolved(undefined) になる
4. `.then(() => { throw new Error('Oh No!') })` → rejected(Error) になる
5. `.catch(error => 3)` → エラーをキャッチし、resolved(3) を返す
6. `.finally(() => console.log(4))` → **4** を出力。finallyは前のPromiseの値を変更せず、resolved(3) がそのまま次に渡る
7. `.then(console.log)` → **3** を出力

ポイント: 同期処理（console.log(7)）がPromiseチェーン（マイクロタスク）より先に実行される。catchでエラーを処理すると正常系に戻り、finallyは値を通過させる。

#### Q. 次のコードの出力は何になりますか？

```javascript
const obj = { a: 1, b: 2, c: 3 };
const { a, ...rest } = obj;
console.log(rest);
console.log(obj);
```

**回答:**

`{ b: 2, c: 3 }` と `{ a: 1, b: 2, c: 3 }`

分割代入のレスト構文（`...rest`）により、`a`を除いた残りのプロパティが浅いコピーで`rest`に格納されます。元のオブジェクト`obj`は変更されません。スプレッド/レスト構文はシャローコピーであるため、ネストしたオブジェクトは参照が共有される点に注意が必要です。

#### Q. 以下のdebounce関数を実装してください

```javascript
// debounce(fn, delay)を実装する
// 使用例: const debouncedFn = debounce(() => console.log('called'), 300);
```

**回答:**

```javascript
function debounce(fn, delay) {
  let timerId;
  return function (...args) {
    clearTimeout(timerId);
    timerId = setTimeout(() => fn.apply(this, args), delay);
  };
}
```

最後の呼び出しから`delay`ミリ秒後に`fn`を実行します。`delay`以内に再度呼ばれるとタイマーがリセットされます。`fn.apply(this, args)`で元のthisコンテキストと引数を保持します。検索入力のオートコンプリートやウィンドウリサイズイベントなど、高頻度で発火するイベントの処理に使われます。throttleとの違いは、throttleが一定間隔で最低1回は実行するのに対し、debounceはイベントが止まるまで実行を遅延させる点です。

#### Q. 以下のPromise.allとPromise.allSettledの違いを説明し、それぞれの出力を答えてください

```javascript
const p1 = Promise.resolve(1);
const p2 = Promise.reject('error');
const p3 = Promise.resolve(3);

// パターン1
Promise.all([p1, p2, p3]).then(console.log).catch(console.error);

// パターン2
Promise.allSettled([p1, p2, p3]).then(console.log);
```

**回答:**

パターン1: `error`（1つでもrejectされると即座にcatchに入る）
パターン2: `[{status: "fulfilled", value: 1}, {status: "rejected", reason: "error"}, {status: "fulfilled", value: 3}]`（全てのPromiseが完了するまで待ち、各結果をオブジェクトで返す）

| メソッド | 挙動 |
|---|---|
| `Promise.all` | 全て成功→結果配列、1つでも失敗→即reject |
| `Promise.allSettled` | 全て完了まで待ち、各結果のステータスを返す |
| `Promise.race` | 最初に完了（成功/失敗問わず）したものを返す |
| `Promise.any` | 最初に成功したものを返す。全て失敗→AggregateError |

#### Q. 次のコードの出力は何になりますか？thisの挙動を説明してください

```javascript
const obj = {
  name: 'Alice',
  greet: function() { console.log(this.name); },
  greetArrow: () => { console.log(this.name); }
};
obj.greet();
obj.greetArrow();
const greet = obj.greet;
greet();
```

**回答:**

`Alice`, `undefined`, `undefined`

- `obj.greet()`: メソッド呼び出しなのでthisはobjを指し、`Alice`を出力
- `obj.greetArrow()`: アロー関数はレキシカルスコープのthisを参照する。オブジェクトリテラルはスコープを作らないため、定義時の外側スコープ（グローバル/module）のthisを参照し`undefined`
- `greet()`: 関数が変数に代入されて単独で呼び出されると、thisバインディングが失われる。Strictモードではthisは`undefined`、非Strictモードではグローバルオブジェクト（nameプロパティは通常undefined）

## System Design

### システムデザイン面接の回答フレームワーク

システムデザイン面接では、以下のステップで回答を構成します。

1. **要件の明確化（3〜5分）**: 機能要件（何ができるか）と非機能要件（スケーラビリティ、可用性、レイテンシ等）を面接官に確認する。曖昧なまま設計を始めない
2. **概算見積り（3〜5分）**: DAU（日次アクティブユーザー）、QPS（秒間クエリ数）、ストレージ容量、帯域幅の概算を計算する
3. **ハイレベル設計（10〜15分）**: コンポーネント図を描く。クライアント、ロードバランサー、Webサーバー、データベース、キャッシュ、メッセージキューなどの主要コンポーネントとそのデータフローを示す
4. **詳細設計（10〜15分）**: 面接官が興味を示したコンポーネントを深掘りする。データモデル、API設計、アルゴリズムの選択を議論する
5. **スケーリングとボトルネック（5分）**: 単一障害点の特定、スケーリング戦略（水平/垂直）、キャッシュ戦略、データベースのシャーディング/レプリケーションについて議論する

### 練習すべき代表的な問題

- URL短縮サービスの設計（ハッシュ生成、リダイレクト、スケーリング）
- チャットシステムの設計（WebSocket、プレゼンス管理、メッセージ配信）
- SNSのニュースフィード/タイムラインの設計（プッシュ vs プル、ファンアウト戦略）
- 通知システムの設計（複数チャネル、優先度、リトライ）
- レート制限システムの設計（トークンバケット、分散環境での実装）
